# ASR 与验收方案

以下是设计目标和验证计划，不是已通过的测试报告。验证后在 `evidence/` 保存环境、输入、步骤、实际值、结论和截图；失败也要保留，不只记录成功页面。

## 1 影响架构的需求

### ASR-01 监测故障隔离

场景：监测进程停止，数据库和评分模型仍正常，用户继续提交合法请求。

响应：评分和审计事务能提交，事件保留在 outbox；worker 恢复后补算。设计采用独立进程和持久化 outbox，不使用仅存在内存中的任务列表。

验证：停止 worker 后提交 100 个不同幂等键的请求，成功保存 100 条评分与对应待处理事件；恢复后每个事件仅累计一次。数据库失败不属于本项可用性承诺。

责任：A 主验，B 核对事务与记录数。

### ASR-02 幂等与一致性

场景：网络重试或 worker 中途退出后重复处理。

响应：重复请求返回原结果；重复消费不重复增加计数、告警或审计证据。依靠业务唯一约束和事务，不宣称消息传递天然恰好一次。

验证：同一请求重复十次，只有一个评分编号；同键异内容返回 409；消费同一事件十次，统计只加一次。注入事务提交前异常，确认评分、快照、初始审计和 outbox 均回滚。

责任：双方共同完成。

### ASR-03 决策可追溯与复现

场景：激活新模型后，审计人员检查旧版本评分。

响应：检索原输入、版本、阈值和解释，使用原包复现；符合指定环境时误差不超过 `1e-8` 且阈值判断一致。模型文件不存在、摘要或环境不符时明确失败。

验证：从两个版本各抽取十条评分；切换激活版本后复现。另模拟包引用缺失与摘要不符，均不能回退到当前模型。

责任：B 主验，A 提供推理和包校验。

### ASR-04 访问控制

场景：未登录用户、无模型授权用户和普通模型人员访问审计与规则接口。

响应：认证与授权在 API 层检查，分别返回 401/403；管理员变更和审计导出留痕。

验证：直接 HTTP 调用接口，覆盖未登录、过期令牌、无角色、无模型权限、合法审计人员等场景。不能仅测试页面按钮。

责任：B 主验，A 从调用端交叉检查。

### ASR-05 响应性能

场景：本地单 API、单 worker、模型常驻内存、数据库约一万条记录，五个并发客户端持续提交合法模拟评分。

建议目标：预热后至少 500 次请求，端到端成功请求时延 P95 不超过 500 ms，API 服务错误率低于 1%。这是待测目标，不能提前写成结论；失败重试会改变统计口径，压测时不得隐藏失败样本。

测量：记录机器配置、依赖、请求数量、并发数、成功/失败数、P50/P95/最大耗时；端到端时间包含模型与落库，不含界面渲染。监测 worker 的推理耗时图不能作为本项证据。

责任：A 执行请求脚本，B 保存与核对结果。

### ASR-06 监测时效与样本充分性

场景：正常运行下某个已闭合窗口满足至少 200 条有效样本，指标超过预设规则。

建议目标：60 秒窗口闭合并经过十秒迟到宽限后，十五秒内生成对应指标与告警；记录事件完成时间和告警时间验证。进程故障期间的补算时效单独测，不计入正常目标。

响应：样本不足显示状态，分母为零不生成无意义比例，迟到事件修订原窗口。

责任：A 主验，B 查证时间和关联数据。

### ASR-07 规则与版本可扩展

场景：增加一个监测指标或调整阈值。

响应：指标计算采用统一输入输出接口，规则版本化；新规则不覆盖历史依据，旧窗口重算仍可解释。

验证：新增预测概率 PSI 或新增缺失率规则，不改评分请求格式；查询旧告警能看到原阈值和规则版本。

责任：A 主验，B 检查数据兼容。

## 2 功能与异常检查清单

- [ ] T01 正常评分：合法输入生成概率、解释、版本与证据，数据库关联完整。
- [ ] T02 输入校验：负金额和越界字段返回 422；null 按约定填补并计入缺失。
- [ ] T03 缺失告警：成功评分样本字段缺失率超过演示阈值，显示真实分子分母。
- [ ] T04 漂移告警：使用固定分箱的参考和漂移样本计算 PSI；正常样本不保证绝对不告警，结果与独立手工样例核对。
- [ ] T05 失败率：注入约 5% 推理失败，概率为空，失败率口径正确。
- [ ] T06 停 worker 与恢复：满足 ASR-01；未完成事件和租约可恢复。
- [ ] T07 重复与冲突：满足 ASR-02；同键异内容拒绝。
- [ ] T08 事务回滚：持久化任一步骤异常不留下半条完整业务记录。
- [ ] T09 处置流程：告警认领、关闭有权限和状态校验，无说明不能关闭。
- [ ] T10 历史复现：满足 ASR-03；复现结果与历史记录分别保存。
- [ ] T11 权限绕过：直接访问 API 仍受控，详情与导出执行同样授权。
- [ ] T12 历史不可覆盖：规则更新新增版本，原始评分不提供修改接口。
- [ ] T13 迟到事件：宽限期后补到的事件能修订原窗口，不重复告警。
- [ ] T14 小样本和空窗口：不产生除零、无穷或 NaN；无数据时界面说明状态。
- [ ] T15 依赖检查：另一人的干净虚拟环境可安装锁定依赖，加载模型并启动。

## 3 验证工具与证据

pytest 用于事务、幂等、权限、固定分箱和复现等有实际意义的验证；httpx 用于接口与端到端时延采集。文档版式和简单页面文案采用人工检查，不为它们编写镜像实现的测试。

证据文件建议命名 `T06-worker-recovery-日期.md` 等，内容包含：执行人、检查人、提交版本、环境、初始条件、命令、期望、实测、截图或日志、限制。性能数据保存原始 CSV 后再汇总。

全部采用合成数据；截图遮蔽令牌、密码和机器敏感路径。测试账号凭据单独传递，不写进报告正文。

## 4 建议八分钟演示

1. 第 0—1 分钟：A 介绍场景、角色和两个固定模型版本，说明数据为合成。
2. 第 1—2 分钟：A 触发正常评分，展示输出、版本与记录编号。
3. 第 2—4 分钟：A 回放已准备的缺失或漂移数据，展示窗口、样本数、指标与告警；窗口等待时间用预先生成的历史窗口辅助演示，明确其来源。
4. 第 4—5 分钟：A 认领并关闭告警，填写具体结论。
5. 第 5—7 分钟：B 从评分编号查询证据，切换激活版本后复现历史记录，展示一致与失败两类结果。
6. 第 7—8 分钟：B 展示无权限请求被拒绝和审计导出；两人说明单机限制与扩展路线。

## 5 报告写作检查

报告中的每个主要需求应能对应功能、数据流、ASR 或架构决策；图里每个组件应在技术和部署说明中有落点。不要把计划阈值写成实测指标，不把合成模型效果写成真实金融效果，不把没有实现的扩展画成当前已部署组件。
