# 双人协作与集成验收

## 1 当前协作基线

截至 2026 年 11 月 11 日，A1 至 A5 已交付合成数据、两个固定模型包、评分与激活 API、SQLite 参考存储、演示认证、独立监测 Worker、规则和告警，以及三个页面。现有回归记录为 108 项通过，新版界面与需求初稿已保存至项目目录。

当前远程分支为 `A/model-monitoring`、`B/audit-platform` 和 `main`。本次协作材料与既有 A 交付一起提交到 A 分支。B 分支目前仍在初始设计基线，B1 至 B5 的正式实现、双方人工交叉检查和最终集成验收均待实际执行后登记。

A、B 为开发职责标识，正式报告由实际成员填写姓名、学号、工时和检查意见。现有提交、测试和截图作为可核对的贡献证据。

## 2 职责和交叉检查

### 2.1 成员 A

A 负责特征和数据口径、固定 Pipeline、模型完整性检查、评分与解释、监测统计、规则与告警、模型和监测页面，主笔业务架构、逻辑架构与一级数据流图。

交给 B 的实物包括 `data/synthetic/v1`、`artifacts/credit-logreg-v1`、`artifacts/credit-logreg-v2`、`app/contracts.py`、A3 至 A5 交接说明、`examples/` 与 `evidence/`。B 检查模型环境、样例概率、事件字段、原始缺失信息及告警关联，记录实际结果。

A 在 B 交付后负责检查正式身份是否能被当前 API 和页面识别、存储适配是否保留评分事务、旧记录是否可追溯，以及复现是否调用原版本 Pipeline。模型、参考分箱和统计计算方面的问题由 A 主修。

### 2.2 成员 B

B 接手现有存储和配置基线，完成正式用户、角色与模型授权、审计查询与导出、历史评分复现任务、相关页面和部署说明，主笔数据架构、技术架构与部署架构。B1 至 B5 的实施状态见分工文档。

B 先核对并复用 `app/storage/sqlite_store.py` 与 `app/modules/monitoring/store.py` 的现有能力，再补充实际缺口。已有评分、快照、审计、outbox、幂等回执和窗口修订共同使用当前数据关系。需要调整表结构时，提交迁移步骤、旧库兼容样例和回归结果。

B 负责整理报告合并稿，A 核对模型、指标和图文描述。双方各自演示负责的功能，并共同解释从评分、事件到告警和审计证据的完整数据关系。

### 2.3 共享文件

`app/main.py`、`app/contracts.py`、`app/config.py`、共享 SQLAlchemy 元数据、`docs/04-数据与接口约定.md`、依赖锁和需求说明书由本次任务的主责成员修改。另一成员在合并检查中核对调用方、数据库和文档是否一致。

A 已为可运行原型交付部分原规划由 B 管理的存储、认证和配置基线。B 后续贡献按正式平台补齐、迁移与联调记录说明，现阶段的参考适配器按现有交付记录登记。

## 3 B 接手操作

### 3.1 同步开发基线

B 在自己的工作副本中执行以下步骤，将 A 已交付代码纳入 B 分支。存在本地改动时先自行提交或保存，再进行分支切换与合并。

```powershell
git fetch origin
git switch B/audit-platform
git merge origin/A/model-monitoring
```

合并后读取 README、A3 至 A5 交接说明及当前完整依赖锁 `requirements-a5.lock.txt`。在约定的 CPython 3.12.14 Windows AMD64 环境中创建虚拟环境并安装锁定依赖。

### 3.2 确认既有功能

使用 `python -m scripts.run_acceptance --report evidence/B-baseline-validation.json` 记录接手后的实际结果。先配置两个独立演示令牌并启动 API，再使用同一个数据库与模型目录启动 `python -m app.worker`，最后启动 `python -m streamlit run streamlit_app.py`。

隔离演示可执行 `python -m scripts.preview_a5`。该脚本每次创建新的运行目录，默认端口为 API 18005 和 UI 18505，支持通过参数指定端口。演示结算采用显式推进的测试时钟，其口径见 A5 操作说明。

### 3.3 逐步接入正式平台

先提交 B1 的数据字典与兼容迁移，再接入 B2 身份认证。身份适配器实现 `authenticate(token)`，返回含 `principal_id`、`roles`、`model_ids` 的 `Principal`。`GET /api/v1/me` 继续返回这些服务端字段，便于三个现有页面识别权限。

存储适配器遵循 `PredictionStore` 的初始化、版本查询、历史回执、评分保存、激活和关闭方法。应用工厂通过 `create_app(settings, store=..., authenticator=..., monitoring=...)` 接收适配器。替换预测存储时一并接入监测存储，确保 A4 查询和 Worker 访问相同数据。

随后实现 B3 证据查询与导出，再实现 B4 复现任务。复现读取原评分的输入快照、模型版本和包摘要，调用 A2 固定版本加载与评分能力，保存新计算与原概率的差异。现有 A4 Worker 消费 `prediction.completed`，复现任务的类型、调度和结果持久化由 B 在相应提交中明确。

最后完成 B5 的审计与复现页面、启动配置、三类架构图和报告汇总，每个阶段附一份可以独立复查的结果。

## 4 接口交接检查

### 4.1 评分与事务

A 提供特征顺序、金额单位、允许范围、原始和规范化输入、标准概率与解释样例。B 核对成功评分、推理失败和同键重试时，快照、评分、审计与 outbox 的记录数量以及关联 ID。存储失败的状态与返回结果应符合 A3 既有语义。

### 4.2 事件与监测

双方核对事件模式 1.1、`inference_attempted`、`error_code`、快照摘要和租约令牌。B 接入数据库后检查 `processed_events`、窗口修订、指标与告警修订及幂等回执约束。A 核对 60 秒 UTC 窗口、10 秒宽限、PSI 200 样本下限及冻结规则口径。

### 4.3 身份与页面

B 提供正式身份与模型授权，A 使用管理员、scorer、risk_manager、审计角色核对可见页面和服务端操作权限。每种角色的实际验证由执行人记录，页面按钮与 API 返回结果分别核查。

### 4.4 审计与复现

B 提供按 `prediction_id` 读取证据及复现结果的接口，A 检查版本、输入、阈值、概率与解释快照的关联。切换激活版本后，复现仍应使用历史记录固定的版本。缺包、摘要改变和环境不匹配分别保留失败类别。

## 5 双人联调案例

以下为待双方执行的清单，测试报告中的既有自动化结果可作为基线。实际执行后填写记录编号、操作者、检查者和证据路径。

1. C01 正常评分。提交标准样例，核对完整证据和 outbox，A 负责输入与概率，B 核对事务关联。
2. C02 幂等与故障。相同请求重试、同键异内容、推理失败和存储失败，核对结果数量、错误及回滚。
3. C03 暂停与恢复。Worker 停止时保存评分，恢复后消费并重算，核对消费去重、积压和心跳。
4. C04 缺失与样本不足。核对原始收入缺失率和 PSI 状态，并记录窗口与样本数。
5. C05 规则与迟到修订。新规则在未来窗口生效，历史窗口重算继续使用冻结版本，修订历史可查。
6. C06 告警处置。认领、填写说明、关闭、重复操作和越权操作，核对状态及动作记录。
7. C07 正式权限。核对四类账号的模型范围、详情与导出授权，并检查 `GET /api/v1/me` 与页面状态。
8. C08 历史审计与复现。版本切换后核对旧评分复现、结果比较及明确的依赖失败类别。
